# 向量化性能评测模块

- **模块定位**：用可重复数据对比本地向量化方案，并把优胜方案接入 DocSeek 建库链路。
- **对应代码**：`bench/embedding/`、`src/embedding/`、`src/application/index-documents.ts`。
- **所属 M 里程碑**：[M7 向量化性能优化](../roadmap.md#m7-向量化性能优化)。
- **当前状态**：进行中。
- **最近更新时间**：2026-09-05。

## 职责与边界

- 固定文档片段、质量查询、机器信息和运行参数。
- 分别测量模型加载、向量生成、数据库写入和完整建库时间。
- 使用相同评价方法比较语义召回与排名。
- 记录安装体积、原生依赖和跨平台风险。
- 根据质量门槛与性能结果形成可解释的选型结论。
- 候选依赖只用于评测，选型完成前不进入正式 npm 包。
- 不修改 Markdown 分块规则、混合排序公式和默认搜索输出。

## 结构与数据流

```text
保留的 InferForge index.db
  -> 读取并固定 1,598 个片段
  -> 生成样本指纹
  -> 候选适配器批量向量化
  -> 固定概念短语查询
  -> 计算纯语义排名与质量指标
  -> 分离记录向量生成和 SQLite 写入
  -> JSON 原始结果 + Markdown 选型结论
```

完整 DocSeek 复验在候选通过纯向量评测后进行，用候选向量重建临时索引，再运行现有混合检索质量流程。InferForge 当前索引只读使用，不删除、不覆盖。

## 关键决策

### 先固定模型，再比较模型

第一轮尽量使用同一模型、精度、前缀和输入顺序，判断向量化工具本身的模型加载、分词、批处理与推理开销。第二轮才允许模型不同，用完整质量集衡量中英文技术文档效果。这样每一项差异都有明确来源。

### 质量是硬门槛

候选至少达到 M4 已有门槛：正向 Recall@5 不低于 0.90、第一名命中率不低于 0.70、精确术语第一名命中率不低于 0.90、无答案识别率不低于 0.90、稳定性为 1.00。InferForge 还会增加短概念、同义表达、项目黑话和中英文混合查询。

纯向量评测无法判断无答案时，单独报告 Recall@5、第一名命中率和平均倒数排名；无答案识别必须在完整混合检索复验中通过。

### 不用单一综合分掩盖取舍

报告先列出质量不达标项，再展示达标候选的耗时、吞吐、内存和安装成本。若多个候选互有优劣，保留并列结果和业务取舍，不用随意权重压成一个看似精确的总分。

### 冷热数据分开

- 首次下载：本机没有模型缓存，记录下载耗时、下载量和失败情况。
- 冷启动：已有模型文件，新进程首次加载并生成一个查询向量。
- 温缓存建库：模型文件已存在，新进程完成全部文档向量生成和写库。
- 温查询：同一进程模型已加载，连续生成查询向量。

模型下载时间不计入建库性能目标，但会参与安装体验判断。

## 当前实现与基线

当前生产候选为 `@huggingface/transformers` 4.2.0 的底层 tokenizer 与模型接口，通过 `onnxruntime-node` 1.24.3 在 CPU 上运行 `Xenova/multilingual-e5-small` q8，输出 384 维向量。默认批量大小为 8，最大输入为 288 token。

InferForge 固定样本现状：

| 项目                 |           当前值 |
| -------------------- | ---------------: |
| Markdown 文档        |              126 |
| 文档总大小           |   1,567,507 字节 |
| 检索片段             |            1,598 |
| 片段正文             |     793,030 字符 |
| 扫描、哈希与状态检查 |       约 1.36 秒 |
| 首次建库             | 约 240 至 249 秒 |
| 当前实际推理调用     |           254 次 |

历史实现中 `indexDocuments` 逐份文档调用向量提供者，每份文档内部再按 8 个片段切批，因此实际产生 254 次推理调用。当前生产候选已经改为跨文件汇总、按文本长度分桶，并在向量化后恢复文档顺序。

同模型正确性冒烟已经通过：Transformers.js 与直接 ONNX Runtime 对查询 `SLA违约退款` 生成的 384 维向量余弦一致度为 `0.9999999999999988`。两条路线可以继续做速度对照；FastEmbed 对相同权重采用不同池化方式，归入带质量复验的方案对比。

首轮完整单次数据如下。质量是 18 条 InferForge 纯语义查询的结果，用于候选横向比较；它没有混入 FTS，不能替代 M4 完整质量门槛。

| 工具与模型                      | 批量 | 文档向量耗时 | 片段/秒 |  峰值内存 | Recall@5 | Top-1 |   MRR |
| ------------------------------- | ---: | -----------: | ------: | --------: | -------: | ----: | ----: |
| Transformers.js + e5-small q8   |    8 |     253.0 秒 |     6.3 | 1,184 MiB |    0.556 | 0.333 | 0.478 |
| Transformers.js + e5-small q8   |   16 |     277.3 秒 |     5.8 | 1,642 MiB |    0.611 | 0.389 | 0.500 |
| Transformers.js + e5-small q8   |   32 |     286.5 秒 |     5.6 | 2,403 MiB |    0.611 | 0.444 | 0.556 |
| 直接 ONNX Runtime + e5-small q8 |    8 |     294.2 秒 |     5.4 | 1,046 MiB |    0.556 | 0.333 | 0.478 |
| FastEmbed + e5-small q8         |    8 |     338.4 秒 |     4.7 |   850 MiB |    0.444 | 0.333 | 0.397 |

批量加大没有提高当前 CPU 吞吐，内存反而明显上涨。直接 ONNX Runtime 与当前方案质量一致，但速度慢约 16%；FastEmbed 更慢且质量下降，当前均不进入生产切换候选。

node-llama-cpp 已用 BGE-M3 Q4_K_M 做 8 个均匀抽样片段冒烟：模型加载约 12.2 秒，文档向量约 91.0 秒，峰值约 1,109 MiB，查询向量中位数约 348 毫秒。该样本已经远慢于完整建库目标，因此停止全量运行；抽样未覆盖完整质量目标，不能给出质量结论。模型原站大文件下载中断，镜像下载成功后已按远端 SHA-256 校验。

长度分桶会在生成后恢复原片段顺序，减少同一批次为最长片段补齐的无效 token 计算，同时不改变模型、前缀、向量维度和存储协议。

128 个均匀抽样片段的批量 8 冒烟中，按长度分桶把文档向量时间从 20.4 秒降到 15.1 秒，约快 26%，峰值内存从约 1,041 MiB 降到 1,013 MiB。该收益仍不足以达到 M7 目标，继续通过直接 ONNX 路线对比 512 与 256 token 的最大输入长度；正文全文仍进入 FTS，截断对语义召回的影响由完整质量集裁决。Transformers.js 高层管线不公开单次调用的最大长度设置，评测不修改其 tokenizer 私有配置。

随后改用底层 tokenizer 与模型接口，对超长输入保留头尾 token 并在中间插入分隔符。冻结快照来自 InferForge 提交 `260ee675`，包含 136 份 Markdown、1,630,013 字节和 1,677 个片段，语料指纹为 `514dfbf5c4fae56fa6e44b7d583c2a9a27d505b936d568c8eb9884ccb04ad0e7`。

| 最大 token | 批量 | 完整 init | Recall@5 | Top-1 |   MRR | 稳定性 | 结论                 |
| ---------: | ---: | --------: | -------: | ----: | ----: | -----: | -------------------- |
|        512 |    8 |  172.0 秒 |    0.889 | 0.389 | 0.581 |  1.000 | 质量对照             |
|        320 |    8 |  127.3 秒 |    0.889 | 0.389 | 0.582 |  1.000 | 达标但更慢           |
|        288 |    8 |  123.7 秒 |    0.889 | 0.389 | 0.573 |  1.000 | 当前生产候选         |
|        280 |    8 |  121.5 秒 |    0.833 | 0.333 | 0.548 |  1.000 | 召回下降             |
|        272 |    8 |  112.9 秒 |    0.833 | 0.278 | 0.497 |  1.000 | 召回下降             |
|        256 |    8 |  104.8 秒 |    0.833 | 0.278 | 0.502 |  1.000 | 召回下降             |
|        288 |    4 |  124.4 秒 |    0.833 | 0.389 | 0.553 |  1.000 | 批量变化导致召回下降 |

288 token 是该快照上保持 512 token Recall@5 与 Top-1 的最短输入。四次完整建库为 113.3、123.7、164.6、186.4 秒，标准中位数 144.1 秒，约比历史 240 秒降低 40%；最好一次已经超过两倍提速，但运行波动明显，中位数尚未达到 50% 退出标准。

按实际 token 长度分桶可以把补齐量从 386,968 降到 365,248 token，单次完整建库达到 119.6 秒，但 InferForge Recall@5 降到 0.833。批次组合改变会造成微小数值差，在分数接近的候选上足以改变前五顺序，因此该实现已撤回。批量大小现在进入 Embedding 指纹，修改批量后必须完整重建，避免同一索引混入不同批次组合生成的向量。

当前继续保留按文本长度分桶、288 token 和批量 8。后续不再压缩语义输入，优先比较 ONNX CPU 线程设置、热状态与数据库写入；所有结论继续使用三次中位数。

ONNX CPU 线程已完成补充对照。256 个均匀抽样片段中，运行时默认三次为 15.8、16.7、19.1 秒，中位数 16.7 秒；显式设置 8 个操作内线程与 1 个操作间线程为 16.4、17.9、24.3 秒，中位数 17.9 秒且波动更大。2、4、12、16 线程的单次结果也没有形成更好且稳定的收益，因此生产继续使用 ONNX Runtime 默认线程策略。

样本机为 Windows x64、Node.js 24.18.0、AMD Ryzen 7 5800H、16 个逻辑处理器、约 30 GiB 内存，未发现可用的 NVIDIA 运行环境。所有基线和候选结论都必须同时记录机器信息，不能直接外推到其他设备。

## 候选方案

| 方案                         | 第一轮用途                           | 第二轮用途                         | 关注点                                 |
| ---------------------------- | ------------------------------------ | ---------------------------------- | -------------------------------------- |
| Transformers.js              | 当前生产基线；测试批量大小 8、16、32 | multilingual-e5-small 质量基线     | 安装成熟度、管线额外开销               |
| Transformers.js 底层模型接口 | 与直接 ONNX 一样控制输入长度和分桶   | 继续复用当前模型下载与缓存         | 能否减少底层会话维护                   |
| 直接 ONNX Runtime            | 复用同一 tokenizer 与 ONNX 模型      | 可继续测试同系列中英文模型         | 数据搬运、池化实现、维护成本           |
| FastEmbed                    | 支持时参与同模型对照                 | 测 BGE 中文或 multilingual-e5 系列 | 原生 tokenizer、批量吞吐、模型选择限制 |
| node-llama-cpp               | 模型格式不同，不进入同模型结论       | 测 BGE-M3 GGUF 等中英文模型        | 包体积、现场编译风险、CPU 与 GPU 支持  |

无法在当前平台安装、无法离线复用缓存或缺少可靠模型的候选可以记录为未通过，但不能伪造性能数字。

FastEmbed 2.1.0 当前直接依赖旧版 `tar`，默认安装审计包含已公开的高危和严重问题。覆盖到安全版本后，其 ESM 入口又会因为仍使用旧式默认导入而加载失败；隔离评测改走该包的 CommonJS 入口继续取性能数据。生产接入需要维护依赖覆盖与入口兼容处理，这两项都计入安装成本；正式包不能在这些问题未解决时直接采用其默认依赖树。

## 验证方式

- 样本指纹一致时，各候选收到相同数量、相同顺序和相同文本的片段。
- 向量数量、维度、有限数值和单位长度校验通过。
- 批量大小 8、16、32 各运行至少三次温缓存建库，报告中位数和最小至最大范围。
- 查询延迟预热后报告中位数和第 95 百分位。
- 峰值常驻内存由独立候选进程采样，避免多个模型互相污染。
- 质量查询重复两次，排名结果必须稳定。
- 优胜方案接入后运行格式化、静态分析、严格类型检查、单测、构建、npm 包检查和真实质量评测。
- 用 `docseek init` 对 InferForge 文档做最终完整复验，并保留原索引用于前后对照。

## 退出标准

- 至少三条本地向量化方案留下可复现的版本、参数和原始结果。
- 所选方案通过 DocSeek 与 InferForge 两套质量检查。
- InferForge 温缓存完整建库耗时相对约 240 秒基线至少降低 50%。
- 查询延迟、峰值内存和 npm 安装体验没有无法接受的退化。
- 正式实现、配置迁移、测试、文档、提交和远端推送全部完成。

## 待扩展项

- 有 NVIDIA、Apple Silicon 和 Linux 机器后的设备矩阵。
- BGE-M3、量化档位和长文本长度对质量与吞吐的影响。
- 增量更新时跨文件复用相同片段向量。
- 模型下载镜像、断点续传和离线安装体验。
- 大于十万片段时 vec0 与精确向量扫描的查询性能。
