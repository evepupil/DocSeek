# DocSeek 技术设计

## 1. 技术基线

| 范围       | 选择                             | 说明                                       |
| ---------- | -------------------------------- | ------------------------------------------ |
| 运行时     | Node.js 22+                      | 当前 SQLite 驱动要求 Node.js 22 或更高版本 |
| 语言       | TypeScript 严格模式              | 开启全部严格类型检查                       |
| 模块格式   | ESM                              | 面向现代 Node.js 和 npm 发布               |
| CLI        | Commander                        | 命令和参数边界清晰                         |
| SQLite     | better-sqlite3                   | 本地同步访问，部署简单                     |
| 向量能力   | sqlite-vec                       | 使用 SQLite 扩展计算余弦距离               |
| 关键词索引 | SQLite FTS5                      | 本地 BM25 排名                             |
| Markdown   | mdast-util-from-markdown         | 使用语法树和源码位置解析标题及块结构       |
| Embedding  | @huggingface/transformers        | 本地 ONNX 推理，无常驻服务                 |
| 模型网络   | undici                           | 支持环境代理和 Windows 当前用户系统代理    |
| 默认模型   | Xenova/multilingual-e5-small，q8 | 约 118 MB，兼顾中英文与 CLI 成本           |
| 测试       | Vitest                           | 单元测试和本地集成测试                     |

BGE-M3 通过配置使用，推荐 q8 和 1024 维。其模型体积和启动成本更高，MVP 默认配置采用 384 维的 multilingual-e5-small。

## 2. 配置设计

`.docseek/config.toml` 包含配置版本、项目标识、Embedding 设置、分块设置和来源列表。

```toml
version = 1
project_id = "generated-uuid"

[embedding]
provider = "transformers"
model = "Xenova/multilingual-e5-small"
dtype = "q8"
query_prefix = "query: "
document_prefix = "passage: "
batch_size = 8
max_tokens = 288

[chunking]
max_chars = 1800

[search]
vector_weight = 0.45
keyword_weight = 0.55
semantic_best_distance = 0.09
semantic_weak_distance = 0.15
minimum_confidence = 0.50
candidate_pool = 100

[[sources]]
id = "project"
kind = "markdown-directory"
path = "."
include = ["**/*.md"]
exclude = ["**/.git/**", "**/.docseek/**", "**/node_modules/**"]
tags = []
```

MVP 只生成一个 `project` 来源。未来 `add` 只需新增来源配置并调用现有增量索引流程。

## 3. Markdown 分块

1. 使用 Markdown 语法树读取标题和块级节点的源码位置。
2. 维护标题栈，生成完整标题路径。
3. 每个标题到下一个标题之间形成一个基础章节。
4. 长章节按块级节点组合，达到字符上限后开始新片段。
5. 单个超长块按行切分，保证任何片段都能进入模型输入范围。
6. 向量输入由标题路径和片段正文组成，输出定位仍使用原始源码行号。
7. 输入超过 `max_tokens` 时保留 token 序列头尾并在中间插入分隔符，避免只保留章节开头。

字符上限只用于处理超长章节，章节边界始终优先。

## 4. 中文关键词索引

FTS5 使用预处理后的检索文本：

- 英文、数字和代码标识符保留为标准词项。
- 驼峰和分隔符中的子词额外保留。
- 中文连续文本加入 ICU 分词结果。
- 中文连续文本加入双字组合和较短完整词组。
- 标题词项与正文词项分列存储，BM25 对标题赋予更高权重。

查询经过相同预处理后，以安全引用的 OR 表达式提交给 FTS5。

## 5. 向量与结果融合

sqlite-vec 保存 Float32 向量并计算余弦距离。项目文档规模较小时使用带筛选条件的精确扫描，减少索引结构限制；未来数据量扩大后可以迁移到 vec0 虚拟表，调用层保持不变。

查询词先删除单个汉字、常见问句词和过短词项。两路候选采用加权 Reciprocal Rank Fusion，关键词略高于语义：

```text
rrf = 0.45 / (60 + vector_rank) + 0.55 / (60 + fts_rank)
score = 0.35 * normalized_rrf
      + 0.50 * lexical_strength
      + 0.15 * semantic_strength
```

`lexical_strength` 根据查询词在标题和正文中的实际覆盖计算，项目标识符和较长中文词权重更高。`semantic_strength` 把默认模型的余弦距离映射为 0 至 1。最终分数使用理论范围，不按本次第一名重新归一化。

候选需要达到最低可信度。向量和关键词都排在前列时允许较低门槛，兼顾同义改写；低可信候选全部过滤。检索配置不进入 Embedding 指纹，修改权重和阈值不要求重建索引。未知模型可以通过 `[search]` 单独校准距离阈值。

## 6. 检索质量评测

- `eval/search-quality.json` 保存问题、类型、期望文件和期望标题，不保存大段答案。
- `npm run eval:quality` 使用真实模型更新当前项目索引，复用同一个模型会话执行全部问题。
- 报告前五命中率、第一名命中率、平均倒数排名、无答案识别率、稳定性和阶段耗时。
- 真实模型评测独立于 `npm run gate`，避免发布门禁依赖网络和本机模型缓存。
- 单元测试继续使用固定候选和固定向量，约束融合公式、过滤边界和输出协议。

首批 24 条自测结果达到全部门槛。复用索引阶段保存的词项后，融合阶段中位数降至约 2 至 3 毫秒；缓存搜索总耗时连续两轮中位数约 16 至 35 毫秒，第 95 百分位约 33 至 56 毫秒。单进程首次搜索仍需加载 ONNX 模型，显式诊断实测约 1.7 秒；该成本不通过引入后台服务规避。

## 7. 增量更新

- 扫描结果先计算文件 SHA-256。
- 数据库以来源标识和来源内相对位置唯一识别文档。
- 哈希相同的文件直接跳过。
- 新增或修改文件先统一解析，再把全部变化片段按文本长度排序并批量生成向量，最后恢复到原文档顺序。
- 删除文件通过外键级联清理片段、向量、FTS 和标签关联。
- 每个文件的数据库替换在事务中完成。
- 初始化使用临时数据库，成功关闭后替换正式数据库。

Embedding 配置会生成指纹。模型、精度、前缀、最大 token 数或向量实现版本变化时，增量更新会拒绝混用旧向量，并提示完整初始化。

## 8. 扩展接口

内部使用以下稳定数据边界：

- `DocumentSource`：发现文档，MVP 实现 Markdown 目录来源。
- `DiscoveredDocument`：提供稳定身份、通用位置、展示路径、内容和标签。
- `DocumentParser`：把来源内容转换成可索引片段。
- `EmbeddingProvider`：分别生成查询与文档向量。
- `IndexStore`：作为存储入口保存集合、来源、文档、片段、标签和向量；搜索 SQL 单独放在查询模块。
- `SearchRequest`：包含查询、数量、集合、来源、标签和路径筛选。

外部目录和单文件可以复用 Markdown 解析器。项目记忆可以实现新的来源与解析器。全局检索可以把同一套存储指向用户级数据库。

## 9. 发布与兼容

- npm 包名使用 `docseek`，命令名同为 `docseek`。
- `bin` 使用 npm 接受的 `dist/index.js` 相对路径；发布门禁固定检查命令映射和可执行首行。
- 发布内容只包含编译产物、README、LICENSE 和必要元数据。
- 包元数据指向公开 GitHub 仓库、README 和 Issues，公开访问级别写入发布配置。
- 原生 SQLite 依赖保持外部依赖，不打入 JavaScript 包。
- `npm pack --dry-run` 检查发布文件。
- 首次使用默认模型需要联网下载，后续使用本机缓存。
- Windows 优先读取标准代理环境变量，未配置时读取当前用户系统代理；代理信息不写入配置或日志。
- 模型缓存默认放在用户缓存目录，可以通过 `DOCSEEK_MODEL_CACHE` 调整。
- Hugging Face 地址可以通过 `DOCSEEK_HF_ENDPOINT` 或 `HF_ENDPOINT` 调整。
- 本地索引和模型缓存不提交 Git。

## 10. 紧凑导航输出

- 默认文本输出根据 `/` 拆分文档路径，再接入去重后的 Markdown 标题层级。
- 文件名与第一层文档标题规范化后相同时，省略重复标题。
- 每个检索片段形成一个 `L起始-结束` 叶子；单行使用 `L行号`。
- 目录、文件和章节节点从后代叶子计算命中数量和算术平均分，格式为 `×数量 .平均分`。
- 没有自身行区间且只有一个子节点时，将连续目录、文件和章节合并到一行；合并后只有一个行区间时，直接在该行显示位置和分数，省略可推导出的 `×1` 与重复平均分。
- 根节点使用所有结果的最长共同目录；没有共同目录时使用 `./`。
- 同级分支按后代最高分、平均分、命中数和名称稳定排序；章节自身的行区间也参与同级排序。
- 默认搜索不做最终条数截断，但向量与关键词各自只从 `candidate_pool` 召回有限候选。
- `--top` 在聚合前按全局排序截断；`--snippet` 和 `--explain` 保留详细平铺输出；`--json` 保持原协议。

## 11. Agent 全局规则注入

- `postinstall` 由 npm 全局安装触发，通过已发布的 JavaScript 包装脚本调用严格 TypeScript 编译产物。
- 包装脚本检查 `npm_config_global`，本地安装直接跳过，避免作为项目依赖或 CI 依赖时修改用户目录。
- 目标解析使用 `os.homedir()`；`CODEX_HOME` 和 `CLAUDE_CONFIG_DIR` 可以覆盖各自配置目录。
- 注入模块持有一份规范化提示词和稳定闭合标签，Codex 与 Claude 共用内容。
- 更新算法分别统计开始和结束标签。零对标签时追加，一对且顺序正确时替换；其他情况返回安全错误且不写文件。
- 写入前使用 `lstat` 拒绝符号链接；缺少父目录和文件时按需创建。
- 换行符从现有文件推断，UTF-8 BOM 和标签外内容按原字节语义保留。
- 生命周期入口逐个处理目标并输出 `created`、`updated`、`unchanged` 或 `skipped`，不打印现有规则正文。
- 手工命令复用同一应用入口，默认只输出提示词，传入 `--install` 时维护两个全局文件。
- Markdown 分块前把 DocSeek 标签区块替换为等量空行；后续标题和正文的源码行号保持不变。
- 发布包必须包含 `dist/instructions` 和生命周期包装脚本，发布清单测试固定校验脚本与文件入口。

## 12. M7 向量化性能评测

评测工具放在 `bench/embedding/`，使用独立依赖和构建配置。根包的生产依赖与 npm 发布清单不包含候选工具，避免试验增加用户安装体积或原生依赖风险。

评测分为两轮：

1. 固定 `Xenova/multilingual-e5-small`、q8、输入前缀和片段顺序，对比当前 Transformers.js 管线、直接调用 ONNX Runtime 以及其他能加载同一模型的本地工具。该轮用于判断运行工具、批处理和数据搬运成本。
2. 在第一轮表现较好的工具上对比适合中英文技术文档的模型。允许 FastEmbed、llama.cpp 等工具使用其原生模型格式，但必须重新跑全部质量题，结果不能与第一轮的工具开销混为一项结论。

每个候选至少记录：

- 工具、版本、模型、精度、向量维度、批量大小和执行设备。
- 模型首次下载时间与下载量、冷启动和温启动时间。
- 纯文档向量生成耗时、片段每秒、字符每秒和推理批次数。
- SQLite 写入耗时与完整建库总耗时。
- 查询向量延迟的中位数和第 95 百分位、进程峰值内存。
- Recall@5、第一名命中率、平均倒数排名、无答案识别和重复运行稳定性。
- Windows、Linux 和 macOS 的安装方式、原生包体积以及失败时是否会现场编译。

InferForge 样本从保留索引读取已经确定的片段，避免每个候选重复扫描和分块。样本清单、查询集、机器信息、运行参数和结果使用 JSON 留档；可读结论写回模块文档。每个温缓存性能数据至少运行三次，报告中位数和波动范围。

生产切换遵循质量先行：先满足 M4 门槛，再从达标方案中比较速度、内存和安装可靠性。目标是在当前 Ryzen 7 5800H CPU 样本机上，将 InferForge 温缓存完整建库时间从约 240 秒降低至少 50%，且查询质量不低于当前基线。

首轮生产候选继续使用 `@huggingface/transformers`，从高层 pipeline 改为底层 tokenizer 与模型接口。新增和修改文档跨文件汇总后按文本长度分桶，单批仍为 8；每条语义输入最多 288 token，超长输入保留头尾并插入分隔符。该方案沿用已有模型下载、代理、缓存和 npm 依赖，不引入 FastEmbed 或 llama.cpp 的生产依赖。

冻结 InferForge 快照包含 136 份 Markdown、1,677 个片段。单次完整 `init` 中，512 token 用时 172.0 秒，288 token 最快一次用时 113.3 秒；两者的 18 条混合检索均为 Recall@5 0.889、Top-1 0.389、稳定性 1.000。272 与 280 token 虽更快，但 Recall@5 降到 0.833，因此不采用。288 token 四次运行范围为 113.3 至 186.4 秒，标准中位数 144.1 秒；按实际 token 长度分桶曾跑到 119.6 秒，但 Recall@5 同样降到 0.833，已经撤回。ONNX 默认线程三次小样本中位数优于显式 8 线程，生产不固定线程。M7 继续拆分写库计时、控制运行波动并补跨平台验证。
