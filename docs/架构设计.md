# DocSeek 架构设计

## 1. 系统概览

DocSeek 是单进程 CLI。一次命令完成项目发现、文档读取、索引更新或搜索，命令结束后不保留后台进程。

```text
CLI
  -> 应用用例
  -> 来源发现 / Markdown 解析 / Embedding / 混合检索
  -> SQLite + sqlite-vec + FTS5
```

## 2. 分层

### 2.1 命令行层

负责命令、参数、退出码和文本或 JSON 输出。命令行层不直接拼接 SQL，也不处理 Markdown。

### 2.2 应用层

包含初始化、增量更新、状态检查和搜索四个用例。应用层编排各模块，并把结果转换为稳定业务结构。

### 2.3 领域层

定义集合、来源、文档、片段、标签、Embedding 和搜索请求。领域对象不依赖 Commander、SQLite 或具体模型。

### 2.4 基础设施层

包含文件系统来源、Markdown 解析器、本地 Embedding、SQLite 存储和配置文件读写。

## 3. 核心数据层次

```text
Collection（项目或未来的全局集合）
  -> Source（项目目录、外部路径、未来的记忆来源）
     -> Document（Markdown 文件或未来的其他文档）
        -> Chunk（标题感知的可检索片段）
           -> Embedding

Document <-> Tag
Source   <-> Tag
```

每个文档同时保存：

- 来源内稳定位置，用于增量更新和去重。
- 通用定位地址，用于未来接入非项目文件来源。
- 面向使用者的展示路径。
- 内容哈希、时间和大小。

## 4. 索引数据流

```text
定位项目与配置
  -> 读取来源列表
  -> 发现 Markdown 文档
  -> 与数据库哈希比较
  -> 解析新增或修改文档
  -> 按标题和块结构切分
  -> 汇总全部变化片段并按文本长度分桶
  -> 超长输入保留头尾 token
  -> 批量生成 Embedding 并恢复文档顺序
  -> 事务写入文档、片段、向量、FTS 和标签
  -> 清理已删除文档
```

来源发现与后续处理只通过 `DiscoveredDocument` 交接。未来新增 `add` 时，索引主流程保持不变。

## 5. 搜索数据流

```text
自然语言查询
  -> 构造查询 Embedding
  -> 向量候选
  -> 中文与术语词项
  -> FTS5 候选
  -> 词项覆盖与语义强度
  -> 加权排名融合与低可信过滤
  -> 应用路径、来源、标签和集合约束
  -> 定位结果
  -> 文本或 JSON 输出
```

存储层返回完整检索候选，搜索层负责评分、过滤和稳定排序。输出层把默认结果继续聚合为路径与章节树，路径和标题前缀只输出一次；JSON 与显式诊断仍使用逐片段结构。离线评测复用同一搜索执行入口和模型会话，不复制生产排序逻辑。

## 6. 数据库存储

主要表和职责：

| 表                  | 职责                         |
| ------------------- | ---------------------------- |
| `schema_migrations` | 数据库版本                   |
| `metadata`          | 模型指纹、维度、最近更新时间 |
| `collections`       | 项目或未来全局集合           |
| `sources`           | 文档来源配置快照             |
| `documents`         | 文档身份、位置和哈希         |
| `chunks`            | 标题路径、行号和内部正文     |
| `chunk_embeddings`  | Float32 向量                 |
| `chunks_fts`        | 标题和正文关键词索引         |
| `tags`              | 标签名称                     |
| `source_tags`       | 来源标签                     |
| `document_tags`     | 文档标签                     |

标签不进入片段内容。将来增加标签或修改标签时可以直接更新关联表。

## 7. 可靠性边界

- 配置和数据库都有版本号。
- 初始化先构建临时数据库。
- 单文件更新使用事务。
- SQLite 开启外键约束和合理的忙等待。
- 文件路径在存储前规范化，展示时统一使用 `/`。
- Embedding 维度和模型指纹必须与索引一致。
- JSON 只写标准输出，诊断信息写标准错误。
- 任何失败都返回非零退出码。

## 8. 目录结构

```text
src/
  cli/            命令和输出
  application/    init、update、status、search 用例
  domain/         稳定业务类型和接口
  config/         TOML 配置
  project/        项目根目录和 gitignore
  sources/        文档来源
  markdown/       标题解析与分块
  embedding/      本地模型
  evaluation/     质量问题校验、指标和真实评测执行
  storage/        SQLite、迁移和查询
  search/         词项与结果融合
eval/             真实模型检索质量问题集
scripts/          构建清理与离线评测入口
tests/
  unit/
  integration/
docs/
  模块设计/
```

## 9. 扩展路线

### 外部文档

`add` 把目录或文件写入来源列表，现有更新用例自动发现和索引。

### 标签

`add --tag` 写入来源或文档标签。搜索层增加公开的 `--tag` 参数，索引正文和向量无需变化。

### 跨项目与记忆

用户级目录保存全局集合和项目登记表。项目索引器继续产生相同的文档与片段结构，搜索请求通过集合范围决定查当前项目或全部项目。记忆来源只需提供内容和通用定位地址。

## 10. Agent 使用入口

```text
npm 全局安装 / 手工修复命令
  -> 解析当前用户的 Codex 与 Claude 配置目录
  -> 检查全局规则文件和 DocSeek 闭合标签
  -> 新增、替换或保持提示词区块
  -> Agent 新会话自动继承使用规则
  -> status / init / update / search / Read 原文
```

全局规则注入属于 CLI 外围适配层，只负责让 Agent 发现已有命令。规范提示词独立于具体 Agent，目标文件解析通过注册表扩展。未来增加其他 Agent 时新增目标适配器，不改搜索、索引和存储链路。

Markdown 来源进入解析器前会屏蔽 DocSeek 自己生成的规则区块。屏蔽操作只清空区块字符并保留换行，因此项目规则文件中的其他内容仍可检索，已有标题和行号保持准确。

## 11. 性能评测与生产选型边界

```text
固定文档片段 + 固定质量查询 + 机器与运行参数
  -> 候选向量化适配器
  -> 性能记录 + 语义排名
  -> 质量门槛
  -> 达标候选对比
  -> 选定后接入 EmbeddingProvider
```

评测层只依赖统一的“批量生成文档向量、生成查询向量、释放资源”能力。候选工具各自处理模型下载、分词、批处理和推理，评测层负责计时、内存采样、质量计算与结果留档。

评测代码位于 `bench/embedding/`，候选依赖与正式 CLI 隔离。生产代码继续通过 `EmbeddingProvider` 使用最终方案，索引编排、SQLite 存储、混合检索和 CLI 不感知底层工具。更换模型或向量维度仍通过模型指纹要求完整重建索引。

M7 已将索引编排改为跨文件批量：全部新增和修改文档先分块，向量提供者按文本长度分桶，生成后再按原位置还原并逐文档事务写入。未变化文件和纯删除更新仍不加载模型。EmbeddingProvider 边界保持不变，后续替换本地工具无需改索引应用层。
